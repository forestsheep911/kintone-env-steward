# 产品背景

## 问题

kintone 的优势是业务人员可以快速创建和调整 App。相同的灵活性也会让环境治理
逐渐落后于业务变化：字段被重复创建，流程状态失去统一语义，权限沿用旧组织关系，
自定义代码无人维护，测试与生产的配置差异只能靠记忆解释。

传统盘点通常回答“这里有什么”，但治理还需要继续回答：

- 哪些配置偏离了团队认可的基线；
- 偏差是否是风险、合理例外，还是仅需补充说明；
- 谁负责决定，何时整改，如何验证；
- 环境发生变化后，如何知道问题是否复发。

因此产品不应停在一次性报告，也不应直接跳到自动改配置。它需要建立从证据到行动
再到复核的闭环。

## 目标用户

- 负责多个 kintone 环境的管理员；
- 在交付前检查或配置客户环境的实施团队；
- 处理性能、权限、流程和维护问题的支持团队；
- 需要理解现状但不熟悉全部配置细节的业务 App 负责人。

## 产品判断

1. **schema/config 优先。** App 结构、权限、流程和集成是治理主对象。
2. **证据优先。** 结论应追溯到 API、MCP、管理界面观察或用户基线。
3. **规则与解释分离。** 确定性检查由规则完成，Codex 补充语境与沟通。
4. **只读优先。** 先证明盘点和整改建议有用，再逐项开放受控变更。
5. **持续治理。** 快照、差异和例外记录要能重复运行。

## 成功标准

- 管理员能在一次运行后理解环境和主要风险；
- 同一规则跨 App、跨时间运行时结果一致；
- 报告区分事实、推断、建议与未知项；
- 每项整改都有目标、影响、审批点、验证方式和恢复思路；
- 第二次快照能说明环境发生了什么变化。
