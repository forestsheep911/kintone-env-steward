# MVP 路线图

## Phase 0：产品与契约（已完成）

- 建立插件、skill 和安全边界；
- 定义治理对象、证据模型和操作等级；
- 确认 schema/config 治理与业务数据分析的边界。

## Phase 1：只读 App 快照（当前）

- 设计版本化 `environment-snapshot` JSON Schema；
- 用固定版本的 kintone 官方 MCP 完成首批配置读取；
- 为 MCP 未覆盖的设置逐步增加确定性 REST 采集脚本；
- 支持指定 App ID、范围表达式和明确授权的 `*`；
- 对凭据和输出做脱敏检查；
- 为采集器加入离线 fixture 测试。

已验证、待产品化的补充采集器：管理页 CSV 的全量 App 目录与容量、
`/k/admin/system/` 的系统设置摘要，以及 `/admin/` 的磁盘、许可、审计与
登录安全摘要。它们必须先具备版本化 schema、脱敏规范、端点白名单和 fixture
测试，且在报告中标记为 UI 派生证据。

完成标准：一句只读分析请求可以生成可复现、带来源、允许部分失败的配置快照和
本地 HTML 报告，不依赖临时脚本。

## Phase 1.5：身份与权限覆盖

- 采集用户、组织和组的稳定代码、状态、层级与成员关系；
- 识别离职/停用、孤儿、共享和高权限账号；
- 识别空组、重叠组、无负责人组和临时组织残留；
- 把身份主体关联到 App、记录和字段权限；
- 对个人信息做最小化采集和脱敏。

## Phase 2：Diff 与首批规则

- 比较同一 App 的两个时间点或两个环境；
- 建立 10–15 条高信噪比规则；
- 输出 findings、严重度、置信度和证据；
- 支持有负责人、有原因、有到期日的治理例外。

首批规则建议关注：无负责人、字段代码异常、权限过宽、离职账号残留、管理员集中、
组用途不明、无终态流程、未知自定义脚本、环境间自定义项漂移。

## Phase 3：持续治理

- 保存基线和批准例外；
- 支持重复运行与趋势比较；
- 生成整改任务清单和复核结果；
- 扩展到空间、身份目录、插件、Webhook 与跨 App 依赖。

## Phase 4：受控执行

- 只开放少量可恢复、可验证的变更；
- 强制 current/desired diff 和当次审批；
- 写后复核，失败时停止并给出恢复指引；
- 保留人工执行路径。

## 暂缓

- 自动扫描所有记录内容；
- 一键“修复全部”；
- 无差异预览的跨环境同步；
- 用浏览器自动化模拟所有管理操作；
- 业务经营看板。
